# ストローク計画

## 目的
減色画像（10 色）を、できるだけ少ない「1px ペンの直線ストローク」と「色の切り替え」で描く手順に変換する。
描画時間はほぼストローク数に比例する（ゲーム側が 1 ストロークに約 2ms かかる）。

## 原作側の根拠（原作クライアント `ipv3m4.jar` の `interpot.client.board` パッケージ）
- `PenTool.mouseDown`: 押した点を `plot`（1px なら `drawLine(x,y,x,y)`）し、`sx,sy` に記憶。
- `PenTool.mouseDrag` / `mouseUp`: `line(sx,sy,x,y)`（1px なら `drawLine`）。**押した点から離した点まで直線が引かれる**。
  → 「押す → 離す」だけで 1 本の線になる（途中の移動は不要。むしろ有害: [drawing.md](drawing.md)）。
- `EditCanvas.clear()`: 現在色で全面 `fillRect`（CLR ボタン）。

## アルゴリズム（`Core/StrokePlanner`）
1. **CLR 色**: 画像に使われている各色について「その色で CLR した後の計画」を作り、コスト最小のものを選ぶ
   （コスト = ストローク数 + 3 × 色クリック数 + CLR 1）。最頻色とは限らない。
2. **色の順序（貪欲法）**: 未完了の色ごとに「今それを描くと何本か」を数え、最少の色から描く（同数なら画素の多い色）。
3. **ラン（1 色・1 行）**: 画素を 3 種に分ける。
   - 必須 = まだ違っていて、目標がこの色
   - 禁止 = もう正しく、目標が別の色（最終状態なので上書きしない）
   - どちらでもよい = 後で別の色に塗られる画素、または既にこの色で正しい画素
   禁止で区切られた区間ごとに、最初の必須〜最後の必須を 1 本にする。**後の色が上書きする画素を跨いで線を延ばせる**のが肝。
4. **縦横**: 色ごとに横ランと縦ランの本数を数えて少ない方。
5. **再計画（続きから・手直し）**: `PlanFrom(target, 画面の画素)` — 既に正しい画素を「正しい」として同じ貪欲法。
   CLR した方が安いなら CLR 案（`allowClear`）。

ストロークの両端は必ず「必須」画素 = 描く前はその色でない画素。`DrawSession` のフェンスはこれを利用する
（終点がその色になったら、ゲームがそこまで処理した証拠）。

## 効果（スクショ画像、Floyd–Steinberg）
| 方式 | 回数 |
|---|---|
| 旧ツール相当: 1 ドットずつ | 約 51,600 クリック |
| 同色の連続だけをラン化（最頻色で CLR 後） | 33,564 本 |
| 本ツール（CLR 色選択 + 重ね塗り延長 + 縦横選択） | 20,227 本 |

ディザなしでは 約 52,000 → 5,387 本。

## 不変条件とテスト
- 計画を再生すると目標と完全一致（ランダム・ノイズ 0〜100 %・減色グラデーション）: `StrokePlannerTests.FullPlanReproducesTheTarget`, `QuantizedGradientIsReproduced`
- ストロークは看板内の水平/垂直線で、両端は自分の色: `StrokesAreStraightInsideTheBoardAndEndOnTheirColour`
- 単色は CLR のみ: `SolidImageIsJustAClear`。後の色を跨ぐ: `LaterColoursAreBridged`。縦縞は縦: `VerticalRunsAreChosenForVerticalStripes`
- 再計画は正しい画素を残す: `PlanFromKeepsCorrectPixels`

## 改善の余地
- 4px / 8px ペンで広い面を塗る（ペンの形が不規則で、境界の扱いが難しい）。
- 斜めの直線（`drawLine` は Bresenham なので斜めも 1 本で描けるが、画素の一致判定が複雑）。
- 色順を貪欲法以外（ビーム探索など）で最適化。現状でも計算は 0.5 秒未満。
