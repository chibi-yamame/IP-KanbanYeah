# 描画の実行

## 目的
計画どおりにゲームを操作して看板に描き、画面を読み戻して目標と完全に一致させる。安全に中断・再開できること。

## 入口
- `Win/DrawRunner.Run`（検出 → 前面化 → カウントダウン → 再検出 → 入力方式の確認 → `DrawSession.Run`）
- UI「描画開始」（計画あり）/「続きから / 手直し」（計画なし = 画面から再計画）、CLI `--draw`

## クラス
| クラス | 役割 |
|---|---|
| `Core/DrawSession` | 1px ペン選択 → CLR → 色ごとのストローク → 読み戻し → 手直し（最大 `MaxRetouch` 回）。`IBoardIO` 越しに操作 |
| `Core/IBoardIO` | キャプチャ / MoveTo / Down / Up / Sleep / CheckInterrupt |
| `Win/InputDriver` | `IBoardIO` の実装。入力方式 Post / Send、安全装置（低レベルマウスフック、Esc、前面チェック） |
| `Win/DrawRunner` | 上記の段取り、Post 方式の座標系キャリブレーション、失敗時スクショ（`--debug-shot`） |
| `Win/ScreenCapture` | GDI `BitBlt`（CAPTUREBLT、カーソルは写らない） |

## 入力方式（最重要の知見）
### 何が問題だったか（2026-10-25、モック看板で調査）
SendInput（実マウス）で「始点へ移動 → 押す → 終点へ移動 → 離す」を高速に送ると、ストローク間に**余計な線**が出た。
キャンバスのイベントを記録すると `P 69 207 → D 70 212 → R 69 212`: ドラッグ (D) が**次のストロークの終点**の座標で届いていた。
原因は 2 段:
1. Windows の `WM_MOUSEMOVE` は合体され、取り出した時点の最新位置になる。
2. さらに **AWT の `EventQueue` が、未処理の `MOUSE_DRAGGED` を後から来たドラッグで上書きする**（キュー内の位置は元のまま、
   `EventQueue.coalesceMouseEvent` / `Component.eventCache`）。
ゲームの 1 ストローク処理（押下時に 76,800 画素の undo コピー + 全面再描画）が約 2ms かかり、入力の方が速いと必ず起きる。
押す (P)・離す (R) の座標は常に正しかった。

### 対策: PostMessage 方式（既定）
- キャンバス等のウィンドウ（`SunAwtCanvas` など。`ChildWindowFromPointEx` でゲームのウィンドウ内を辿る＝他のウィンドウの
  重なりに影響されない）に `WM_LBUTTONDOWN` / `WM_LBUTTONUP` を直接 PostMessage する。
- **押下中は移動を一切送らない**。PenTool は「押した点 → 離した点」に線を引くので、離すメッセージに終点座標を入れるだけでよい。
  ドラッグイベントが存在しないので AWT の合体の影響を受けない。
- 移動メッセージは「別のウィンドウに入るとき」だけ送る（ボタンのホバー用。キャンバス上では送らない）。
- **実カーソルは動かない** → 描画中もユーザーはマウスを使える（ゲームをクリックすると中断）。
- 発見: JRE 8 の AWT は、投函されたマウスメッセージの lParam を**スクリーン座標**として解釈する（クライアント座標を送ると
  ウィンドウ原点分ずれる。実カーソル位置には依存しない — 3 位置で確認）。理由は AWT 内部の前処理経路の違いと推測。
  念のため `DrawRunner.CalibratePost` が、まだ選ばれていないペンボタン（1px か 4px）をスクリーン座標で押して押下表示を確認し、
  だめならクライアント座標で再試行する。
- 結果: 20,227 ストロークを 44 秒で完全一致（手直し 0 回）。1,162 ストロークで 3.7 秒。

### SendInput 方式（互換用）
- 実マウスを使う。上の問題を避けるため**毎ストローク同期**（終点の画素が色になるまで待つ）→ 画面合成（DWM、vsync）待ちで
  約 18ms/ストローク。1,162 ストロークで 20.8 秒、完全一致。
- PostMessage が効かない環境（将来の別 JRE など）の保険。マウスに触れる・ゲームが前面でなくなると中断。

## フェンス（同期）
- `FenceEvery`（既定 40）ストロークごと、および色の最後に、最後のストロークの**終点画素**がその色になるまで待つ
  （計画上、終点は描く前はその色でない）。入力をゲームの処理速度に合わせ、メッセージキュー（上限 10,000）を溢れさせない。
- `FenceTimeoutMs`（3 秒）で来なければ、エディタがまだあるか確認して続行（取りこぼしは読み戻しで直る）。
- **`MaxFenceTimeouts`（3）回連続でタイムアウトしたら中断**（「ゲームの画面が描画に追いついていません」）。画面が描画を反映しない
  状態で、3 秒待ちを延々と繰り返して止まったように見えるのを防ぐ。
- 色ボタン・ペンボタンはクリック後、押下表示が出るまで最大 `PressTimeoutMs`（1 秒）待って確認（3 回まで押し直し）。
  初版はクリック 40ms 後に 1 回だけ見ていたため、実ゲームで「青を選択できませんでした」と誤って中断した（実際は選択済み。
  ゲームの軽量ボタンの再描画がクリックより遅れる）。2026-10-25 修正。

## 読み戻し検証
- 全ストローク後、キャンバスを 100ms 間隔で 2 回続けて同じになるまでキャプチャ（`Settle`）→ 目標と比較。
- 違う画素があれば `PlanFrom` で再計画して手直し（最大 3 回）。
- E2E で、画面の読み戻しとゲーム内部の `pixels` が完全に一致することを確認済み（不一致数が両者で同じ）。

## 安全装置
| 方式 | 中断条件 |
|---|---|
| 共通 | Esc（`GetAsyncKeyState`）、UI の中止、ゲームのウィンドウ消滅、看板が見つからない（移動・隠れ・閉じた） |
| Post | ゲームのウィンドウ内での物理クリック（低レベルフック、注入イベントは除外） |
| Send | 物理マウス移動（3 イベント以上）・クリック、ゲームが前面でなくなった |

- 中断時は必ずボタンを離す（`finally`）。開始前 2 秒のカウントダウン、開始直前に再検出して位置が同じか確認。
- 「続きから / 手直し」= 画面の今の状態から再計画（中断位置を覚えておく必要がない）。

## 不変条件とテスト
- 模擬エディタ（`tests/FakeEditor`: ベベル付きボタン、1px ペン、CLR）で全体が完全一致: `DrawSessionTests.DrawsTheWholePictureExactly`
- 離すイベントを落としても読み戻しで直る: `LostEventsAreRedrawnAfterReadingBack`
- 中断 → 続きから で完成: `InterruptStopsAndResumeFinishes`。エディタが隠れたら止まる: `StopsWhenTheEditorIsGone`
- 画面が描画を反映しなければ止まる: `StopsWhenTheScreenDoesNotFollowTheDrawing`
- SendInput の正規化座標が正確な画素に当たる: `NormalizedCoordinatesHitExactPixels`
- E2E（本物の `EditCanvas`）: `tools/e2e.sh`（開発環境のテスト）

## 落とし穴・経緯
- モック看板のボタンを軽量コンポーネントにしたら再描画で消え、ツールが「エディタが見つからない」で止まった（安全装置は正しく動作）。
  モックのボタンは重量級 `Canvas` にした。実ゲームのボタンは軽量だが、ゲーム自身の描画は正しい。
- **Java2D の Direct3D パイプライン**: この PC で、画面オフ（夜間）の後に Java のウィンドウが「ボタン等は描くがキャンバスの画像は
  描かない（白いまま）」状態になった。内部の `pixels` は正しく変わるが画面は白 → フェンスがすべてタイムアウト。
  `-Dsun.java2d.d3d=false`（GDI パイプライン）なら起きない。対策: モック看板は既定で d3d=false、フルカラー実験ツールの `launch` も d3d=false で起動、
  ツールは連続タイムアウトで理由を出して中断。実ゲームで起きたら、ゲームの最小化 → 元に戻す / 再起動で直る見込み。
  調査には `KANBANDRAWER_TRACE`（フェンスごとの待ち時間・画面の色）が有効だった。
- SendInput の絶対座標は 0..65535 正規化。区間の中央を狙う（`InputDriver.Normalize`）。
- `Thread.Sleep(1)` の分解能のため描画中は `timeBeginPeriod(1)`。
