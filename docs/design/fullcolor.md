# フルカラー直接書き込み（実験的）

## 目的
看板の 10 色の制限を超えて、フルカラーの絵を看板に書き込む。ペンで描くのではなく、ゲーム（Java 8）の中に入れた小さなプログラム
（**エージェント**）が、看板エディタの画素の配列（`EditCanvas.pixels`、`int[]`、0x00RRGGBB。保存はこれをそのまま 24bit で送る → [SPEC.md](../SPEC.md) 2 章）を
直接書き換える。ゲームのプログラム（jar）は一切改変しない（`-javaagent` は Java の正式な機能）。サーバーへ独自の通信もしない
（保存はゲーム自身の「保存」ボタン = 利用者が押す）。**実験的**: 10 色にない色の看板になる（ゲームの UI では作れない）。

2 つの部品と 1 本のパイプ:
| 部品 | 中身 |
|---|---|
| エージェント（Java） | ゲームと同じ JVM で動く。看板エディタを探し、パイプ越しの要求で書き込む。キー Ctrl+Shift+V でクリップボードの画像も書く |
| 看板屋（C#） | パイプのサーバー。ゲームの起動・ショートカット作成。入力方式「フルカラー（直接書き込み）」で今の合成を送る |
| 名前付きパイプ | 看板屋 = サーバー、エージェント = クライアント。手順は「パイプの手順」 |

## 入口・流れ
- 看板屋の起動時: `AgentLink.Start` がパイプのサーバーを作って待ち受け（入力方式に関係なく、看板屋が開いている間ずっと）。
  同時に背景で `kanban-agent.jar` を書き出し直す（内容が違うときだけ）。
- ゲームの起動: 「InterPot を起動」ボタン、または作成したショートカット。どちらも同じコマンド（`-javaagent` 付き）。看板屋が
  起動していなくてもゲームは普通に動く（エージェントは数秒おきにつなぎに行くだけ）。
- 書き込み: 入力方式を「フルカラー（直接書き込み）」にして「描画開始」→ `MainForm.StartFullColor` が合成を RGB に直して
  `AgentLink.Put` → エージェントが `pixels` を書き換えて `OK`（[drawing.md](drawing.md)「フルカラー」）。
- クリップボード: ゲームの看板エディタにフォーカスがあるとき Ctrl+Shift+V（看板屋は不要）。

## クラス
| クラス | 役割 |
|---|---|
| `Java/KanbanAgent.java` → `Resources/kanban-agent.jar` | エージェント（Java 8 バイトコード、`javac --release 8`）。マニフェスト `Java/kanban-agent.mf` は `Premain-Class: KanbanAgent`。exe に内蔵（csproj の EmbeddedResource、論理名 `KanbanDrawer.kanban-agent.jar`）。jar はコミットする（公式文字の `kanban-text.jar` と同じ） |
| `Win/AgentLink` | パイプのサーバー（接続の待ち受け・再待ち受け・ACL）+ 手順の本体 `AgentSession`（`Stream` 1 本を相手に HELLO を読み、PUT を送って応答を読む。テストはメモリ上のストリームで行う）。`Status` と `StatusChanged` イベント（任意のスレッドから） |
| `Win/GameLauncher` | `InterPot3.jar` の場所の決定、起動、ショートカット（.lnk）作成。`JavaHelper` を使う |
| `Win/JavaHelper` | 既存。`FindJava`（.jar を開く Java）、`Extract`（`%LOCALAPPDATA%\KanbanDrawer` へ書き出し）。`FindJavaw`（同じ場所の `javaw.exe`、無ければ `FindJava` と同じ）を足す |
| `UI/MainForm` | 入力方式「フルカラー」、状態の行・ボタン、`StartFullColor`（[ui.md](ui.md)） |

`AgentLink` は Win32 の API は使わず `System.IO.Pipes`（.NET Framework 4.8 標準）だけ。純粋な手順（`AgentSession`、RGB への変換）は
`Win/` に置くが WinForms に依存しない。

## エージェント（`KanbanAgent`）
### 起動
`javaw -Dsun.java2d.d3d=false -javaagent:<kanban-agent.jar> -jar InterPot3.jar`。`premain(String args, Instrumentation)` が
デーモンスレッド（パイプ用 `KanbanAgent`）を起動し、キー用の AWT リスナーを登録して戻る。
- 引数 `args` は省略可（パイプ名を丸ごと指定するテスト用。例 `-javaagent:kanban-agent.jar=KanbanYeah-test1`）。省略時は
  `KanbanYeah-` + 現在のユーザーの SID（`com.sun.security.auth.module.NTSystem().getUserSID()`、Java 8 の Windows 版に標準）。
  SID が得られなければパイプ連携は無効（キー Ctrl+Shift+V は使える）。
- エージェントのどんな例外もゲームに伝えない（全部 `Throwable` で受けて、標準エラーへ出すだけ）。ゲームの動作に影響しない。
- `-Dsun.java2d.d3d=false`: Direct3D パイプラインで看板の画像が描かれない状態になることがあったため（[drawing.md](drawing.md) 落とし穴）。
  ゲームの見た目・動作は変わらない。

### 看板エディタの探し方
`Frame.getFrames()` の各フレームとその `getOwnedWindows()` の部品木（`Container.getComponents()` を再帰）から、クラス名が
`interpot.client.board.EditCanvas` で `isShowing()` のものを探す（クラスをロードしない。名前の比較だけ）。見つからなければ「エディタなし」。
AWT のイベントスレッド以外から木を辿ってよい（読むだけ）。

### 書き込み（`put`、イベントスレッド上）
1. 受け取った RGB を `int[320*240]`（0x00RRGGBB）に直す（イベントスレッドの外で）。
2. `EventQueue.invokeLater` で次を実行し、完了を待つ（最大 5 秒。待ち切れなければ `ERR busy` を返し、後からその処理が動いても
   書かないよう「取消し」フラグを立てる）:
   1. エディタを探し直す（無ければ `ERR none`。HELLO の後で閉じられた場合）。
   2. `pixels` と `undoBuf` をリフレクションで取る（`getDeclaredField` + `setAccessible`）。長さが 76,800 でない / 幅が 320 でなければ `ERR unexpected canvas size`。
   3. `System.arraycopy(pixels → undoBuf)`（ゲームの「元に戻す」が使う 1 段の退避。原作はペン押下ごとに同じことをする）。
   4. `System.arraycopy(新 → pixels)`、`canvas.repaint()`。
3. 結果 `OK` / `ERR <理由>`（例外は `ERR ` + 例外の文字列を 1 行にして）。

エディタを閉じている最中に PUT が来ても、手順 2-1 で `ERR none`（または例外メッセージの `ERR`）になるだけで、ゲームを壊さない。
フィールド名が違う（ゲームの版が違う）ときも `ERR <NoSuchFieldException…>` で止まる。

### エディタの有無の通知
パイプ用スレッドが約 1 秒おきにエディタを探し、有無が変わったら `HELLO` を送り直す（接続直後にも 1 回送る）。

### クリップボード（Ctrl+Shift+V）
- `Toolkit.getDefaultToolkit().addAWTEventListener(…, AWTEvent.KEY_EVENT_MASK)` で**観測するだけ**のリスナー（キー入力を食べない・ゲームの
  コンポーネントを差し替えない）。`KEY_PRESSED`・`VK_V`・Ctrl と Shift が押されていて、`KeyboardFocusManager` の現在のアクティブウィンドウが
  看板エディタを含むウィンドウのときだけ動く（看板エディタ以外の画面では何もしない）。
- クリップボードの読み出しは別スレッド（遅いことがある）: 画像（`DataFlavor.imageFlavor`）→ 無ければファイルのコピー
  （`javaFileListFlavor` の先頭で `ImageIO.read` できるもの）。どちらも無ければ何もしない。
- 画像を 320x240 に**全体を収める**（縦横比を保ち、中央、拡大もする。双線形補間、大きく縮めるときは半分ずつ縮める）。透明（アルファ）の画素・
  余白は**今の看板の画素のまま**（アルファ合成）。結果の 320x240 を上の「書き込み」の手順 2 で書く（`undoBuf` へ退避つき）。
- 看板屋がなくても動く。失敗は標準エラーに出すだけ（画面には何も出さない）。

## ゲームの起動とショートカット（`GameLauncher`）
### `InterPot3.jar` の場所
設定 `fullcolor.jar`（[ui.md](ui.md)）→ 無ければ `C:\Program Files (x86)\InterPot3\InterPot3.jar` → それも無ければファイル選択（`OpenFileDialog`、
`InterPot3.jar` を選ばせる）。選んだ場所を `fullcolor.jar` に保存する。ファイルが存在しなければ使わない。

### 起動（「InterPot を起動」）
1. Java: `JavaHelper.FindJavaw()`（.jar を開く Java の `javaw.exe`。無ければ `java.exe`）。無ければログ「InterPot を動かす Java（.jar を開くプログラム）が見つかりません」で終わり。
2. エージェントの jar を `%LOCALAPPDATA%\KanbanDrawer\kanban-agent.jar` に書き出す（`JavaHelper.Extract("KanbanDrawer.kanban-agent.jar", "kanban-agent.jar")`）。
3. `Process.Start`（`UseShellExecute = false`、作業フォルダ = `InterPot3.jar` のフォルダ、引数 `-Dsun.java2d.d3d=false -javaagent:"<agent jar>" -jar "<InterPot3.jar>"`）。
   `JavaHelper.Start` のジョブオブジェクトには**入れない**（看板屋を閉じてもゲームは続ける）。標準出力・入力は取らない。
4. ログ「InterPot を起動しました（フルカラー用）。ログインして看板の編集画面を開くと、状態が「接続中: エディタあり」になります」。
既にゲームが動いていても起動する（二重起動の判定はしない。ゲーム自身の仕組みに任せる）。

### ショートカット（「ショートカットを作成」）
デスクトップ（`Environment.SpecialFolder.DesktopDirectory`）に「InterPot3 (フルカラー).lnk」を作る（既にあれば上書き）。
作成は `WScript.Shell` の COM（`Type.GetTypeFromProgID`、遅延バインド。参照の追加なし）:
| 項目 | 値 |
|---|---|
| ターゲット | 起動と同じ Java（javaw） |
| 引数 | 起動と同じ `-Dsun.java2d.d3d=false -javaagent:"<agent jar>" -jar "<InterPot3.jar>"` |
| 作業フォルダ | `InterPot3.jar` のフォルダ |
| アイコン | `InterPot3.jar` と同じフォルダに `.ico` があればその最初のもの、無ければ同じフォルダの `.exe` の最初のもの、無ければ Java のもの |
作成前にエージェントの jar も書き出す。ログ「ショートカットを作りました: <パス>」。看板屋を閉じていてもこのショートカットでゲームを起動すればエージェントは入る。

## 名前付きパイプ
- 名前: `\\.\pipe\KanbanYeah-<ユーザーの SID>`（例 `KanbanYeah-S-1-5-21-…-1001`）。環境変数 `KANBANYEAH_PIPE`（`\\.\pipe\` の後ろの名前）があれば看板屋はそれを使う
  （テスト用。エージェントの引数と対にする）。
- サーバー = 看板屋（`NamedPipeServerStream`、`PipeDirection.InOut`、`PipeTransmissionMode.Byte`、`PipeOptions.Asynchronous`、最大インスタンス数 1、
  バッファ 64KB）。
  - ACL（`PipeSecurity`）: 現在のユーザーの SID だけに読み書き（`ReadWrite | CreateNewInstance`）を許可。ネットワークからの接続（`NetworkSid`）は明示的に拒否。
    他のユーザー（管理者でないアカウント、別のログオンのユーザー）はつなげない。
  - 同時に 1 接続だけ。つながっている間は次の接続を待たない（エージェントはゲーム 1 つにつき 1 つ。ゲームを 2 つ起動したときは先の方だけが
    つながり、後の方は「パイプが使用中」で 3 秒おきに試し続ける）。切れたら新しいサーバーを作って待ち受け直す。
  - **看板屋が複数起動しているとき**: パイプを最初に作った看板屋だけがサーバーになる。後から起動した看板屋は作成に失敗し（`IOException`）、
    状態を「未接続（別の看板屋が使用中）」にして、5 秒おきに作り直しを試す（先の看板屋が閉じたら引き継ぐ）。
- クライアント = エージェント。Java 8 にはパイプ用の API がないので、Windows ではパイプがファイルとして開けることを使う:
  `new RandomAccessFile("\\\\.\\pipe\\" + name, "rw")`。開けない（パイプがない = 看板屋が起動していない / 使用中）ときは **3 秒後**に再試行（無限）。
  - Windows の同期ハンドルは、読み待ちの間は同じハンドルへの書き込みも待たされる（I/O がハンドル単位で直列化される）。エージェントは 1 本のスレッドで
    「読む前に `new FileInputStream(raf.getFD()).available()`（`PeekNamedPipe`）で届いているか見る（50ms おき）→ 届いていれば読む」を繰り返し、読み待ちで
    固まらないようにする。HELLO の送信も同じスレッド。
  - 読み書きの途中でエラー（`IOException`）になったらパイプを閉じ、3 秒後につなぎ直す（看板屋が閉じた・ゲームから見て切れた、など）。

## パイプの手順（プロトコル版 1）
### 形式
- 「行」= ASCII の文字列 + `\n`（`\r` は付けない）。1 行は `\n` を含めて最大 256 バイト。文字は ASCII のみ（エラーの理由もローマ字・英語。
  日本語に直すのは看板屋）。単語は半角空白 1 つで区切る。
- 画像のバイト列は PUT の行のすぐ後ろ（間に何も入れない）。
- 画像 = 320 x 240、1 画素 3 バイト（R, G, B の順）、行の順は上から下、各行は左から右。230,400 バイト。
- 版 = 整数 `1`。形式を変えるときに増やす。

### エージェント → 看板屋
| 送るもの | 意味 |
|---|---|
| `HELLO <版> editor` / `HELLO <版> none` | 接続直後に 1 回、その後は「看板エディタがある / ない」が変わるたびに。`editor` = 看板エディタが表示中、`none` = ない（ログイン前・編集画面でない） |
| `OK` | PUT が書き込めた |
| `ERR none` | PUT が来たが看板エディタがない（HELLO の後に閉じた）。書き込んでいない |
| `ERR <理由>` | 書き込めなかった（理由は ASCII 1 行、例 `busy`、`unexpected canvas size`、`bad size`、`unknown command`、例外の文字列） |

### 看板屋 → エージェント
| 送るもの | 意味 |
|---|---|
| `PUT 320 240\n` + 230,400 バイト | 画像を書き込む。**最後の HELLO が `editor` のときだけ送る**。応答（`OK` / `ERR …`）を受け取るまで次の PUT を送らない |

### 順序・タイムアウト・異常
| 場面 | 動作 |
|---|---|
| 接続直後 | 看板屋は 5 秒以内に有効な `HELLO` を待つ。来なければ（または形式が違えば）切って再待ち受け |
| 版が違う | 看板屋はログ「ゲーム側の連携プログラムの版（<n>）が看板屋と合いません。「InterPot を起動」で起動し直してください（ショートカットは作り直し不要）」を **1 回だけ**出し、状態を「版が合いません」にして、**何も送らない**（接続は保ったまま。切ると 3 秒おきに再接続して騒がしい）。その後の HELLO は読み捨て、ゲームが終われば（切断）通常に戻る |
| PUT の応答待ち | 看板屋は最大 10 秒。来なければ接続を切って「未接続」に戻る（ログ「ゲームが応答しません」）。応答が `OK` / `ERR …` 以外でも同じ |
| 切断 | 看板屋: 読み取りが 0 バイト / `IOException` → 状態「未接続」、再待ち受け。エージェント: 3 秒後に再接続。PUT の途中で切れたらその書き込みは失敗（ログ「ゲームとの接続が切れました」）。エージェント側は画像を最後まで読めなければ書き込まない（途中の画像を絶対に `pixels` に書かない） |
| エージェントが PUT を受けたとき | 先に 230,400 バイトを全部読む（途中で止まったらパイプを閉じる。10 秒で見切る）→ その後で、エディタの有無に関わらず応答を 1 つ返す（`ERR none` のときも画像は読み切ってから。ストリームの同期を保つ） |
| `PUT` の寸法が 320 240 でない / 数字でない | `ERR bad size` を返して接続を閉じる（画像の長さが分からず同期できない） |
| 知らない行 | `ERR unknown command`（接続は保つ） |
| 行が 256 バイトを超える | 接続を閉じる |

### 看板屋の状態（`AgentLink.Status`）
| 状態 | 画面の表示 | 意味 |
|---|---|---|
| `Disconnected` | 未接続 | パイプはあるがエージェントが来ていない |
| `Busy` | 未接続（別の看板屋が使用中） | パイプを作れなかった |
| `NoEditor` | 接続中: エディタなし | 最後の HELLO が `none` |
| `Editor` | 接続中: エディタあり | 最後の HELLO が `editor` |
| `Mismatch` | 版が合いません | 版の食い違い |
`Put` が使えるのは `Editor` のときだけ（それ以外は呼び出し側が理由をログに出して何もしない）。

## 看板屋側の書き込み（`MainForm.StartFullColor`）
1. 状態が `Editor` でなければ、理由をログに出して終わり（[ui.md](ui.md) のログの表）。
2. 下書きは使わない。今の合成（`BoardDoc` の `Compositor` の結果、`Composite`）の RGB をそのまま 230,400 バイトに直す
   （float を四捨五入して 0〜255。背景色・文字の固定画素も同じ値。減色・ディザ・パレット丸めはしない）。
3. `AgentLink.Put(rgb)`（バックグラウンドで。応答は最大 10 秒待つ）→ ログ。成功したら「看板の「保存」はご自身で押してください。」。
4. 書き込みはペンで描くのと違い、カウントダウン・看板の検出・前面化・Esc の監視はしない（実マウスもメッセージも使わない）。

## 安全
- パイプは**このコンピューターの中の、同じユーザーだけ**（ACL）。ネットワーク・他のユーザーからは使えない。TCP のポートは開かない。
- 受け取るのは 320x240 の画像だけ（寸法・バイト数を厳密に確認）。読みきれない・形式が違うときは何も書かない。
- 書くのはゲームのメモリ上の 1 つの配列だけ。ゲームの jar は変えない。ゲームのサーバーへは何も送らない（保存はゲーム自身の「保存」で、利用者が押す。実ゲームで看板屋が「保存」を押すことはない）。
- `undoBuf` へ退避してから書くので、ゲームの内部の「元に戻す」で書き込み前に戻せる（原作の画面に「元に戻す」のボタンはない。次にペンを押すと退避は上書きされる）。
  保存するまでは再読込（別のページへ移って戻る）でも元に戻る。
- エージェントの jar は看板屋の exe に内蔵（`%LOCALAPPDATA%\KanbanDrawer` に書き出すだけ）。ゲームのフォルダには何も書かない。
- エージェントは例外を握りつぶしてゲームの動作に影響させない。ゲームを閉じればエージェントも終わる（デーモンスレッド）。

## 不変条件とテスト
- `AgentLinkTests`（メモリ上のストリームで `AgentSession` を検証。CI で実行）:
  - HELLO の解釈（`editor` / `none`、変化の通知、版違い、不正な行 / 長すぎる行 / 5 秒来ない）
  - `Put` が `PUT 320 240\n` + ちょうど 230,400 バイトを書く（行の順・RGB の並び）、`OK` / `ERR none` / `ERR <理由>` / 応答なし（10 秒の代わりに短い値を注入）/ 切断の扱い
  - `editor` でない状態では `Put` が何も書かない、版違いでは何も書かない
  - 合成 → RGB 変換（四捨五入、並び、固定画素もそのまま）
  - 実際の名前付きパイプ（テスト用の名前を `KANBANYEAH_PIPE` 相当の引数で渡す）に別スレッドのクライアントでつなぎ、HELLO → PUT → OK の往復と、
    2 つ目のサーバーが作れない（`Busy`）こと
- E2E（開発環境側で管理）: エージェント付きでモック看板（本物の `EditCanvas`）を起動 → 看板屋で書き込み → 看板の内部の `pixels` と目標が
  0 画素差、`undoBuf` に元の画素があること、エディタなし（`none`）のときの `ERR`、Ctrl+Shift+V でクリップボードの画像が収まること。
- Java のエージェントには単体テストを置かない（CI に Java を入れない。E2E で確認）。

## 落とし穴・経緯
- 先行の実験（TCP の `127.0.0.1` + 起動ごとのトークン）はポートの衝突・トークンの受け渡し（ファイル）が面倒で、名前付きパイプ + ACL に置き換えた。
- Windows の同期ハンドルの直列化（上記）を知らずに「読み用スレッド + 書き用スレッド」にすると、HELLO が送れずにデッドロックする。
- ゲームの `-javaagent` は **起動時**にしか付けられない。起動済みのゲームには入れられない（動的アタッチは JRE に必要な部品がなく、使わない）。
  すでに動いているゲームは閉じて、「InterPot を起動」かショートカットで起動し直す。
- `Frame.getFrames()` に出ない場所（別のスレッドグループの AWT）にエディタがあると見つからない → モック看板では問題なし。実ゲームのエディタが見つかるかはログイン後の確認待ち（未テスト）。
- ゲームの版が上がって `EditCanvas` のフィールド名やクラス名が変わると `none` / `ERR` になる（壊れ方は安全側）。
- 10 色以外の色の看板は、ゲームの UI では作れないものなので、他の利用者から見て不自然かもしれない（README に注意書き）。
